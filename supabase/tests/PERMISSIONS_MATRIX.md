## How to regenerate this file

Run against `staging-security` only:

```sql
select permission,
  bool_or(role='superadmin') as superadmin,
  bool_or(role='admin') as admin,
  bool_or(role='encargado') as encargado,
  bool_or(role='tomador_pedidos') as tomador_pedidos,
  bool_or(role='preparador') as preparador,
  bool_or(role='despachador') as despachador,
  bool_or(role='jefe_bodega') as jefe_bodega,
  bool_or(role='logistica') as logistica,
  bool_or(role='contador_rrhh') as contador_rrhh
from private.role_permissions
group by permission
order by permission;
```

## Scoping notes that this table cannot express

A checkmark means the role *can hold this permission*; it does not mean
unrestricted access. The actual row-level scope comes from the `_v2` policies,
not from this table alone. In particular:

- **`jefe_bodega` / `logistica` + `users.read`**: scoped by `usuarios_read_v2`
  to (a) the caller's own row, (b) any row in the caller's own branch, and (c)
  — the new clause — any row where `rol = 'logistica'` regardless of branch
  (the driver/tracking pool `ChoferesPage` manages). It does **not** grant
  `users.create` or `users.manage`: these roles cannot insert, update, or
  delete any `usuarios` row.
- **`preparador` + `shifts.read`**: scoped by `turnos_read_v2` to the caller's
  own branch via `private.can_access_sucursal()`. Read-only: `preparador` has
  no `shifts.open`/`shifts.close`/`shifts.reopen`/`closures.*` permission, so it
  cannot modify a `turnos` row.
- **`tomador_pedidos` + `closures.annotate`**: scoped by
  `cambios_turno_write_v2` to the caller's own turno via
  `private.turno_in_scope()`. `tomador_pedidos` does **not** have
  `closures.correct`: it can register a handover, not correct a historical
  closure.
- **`superadmin` + `clients.*`/`client_addresses.*`**: scoped by
  `clientes_admin_only_v2` / `direcciones_admin_only_v2`, identical to
  `admin`'s scope — full read/manage of the customer directory, no branch
  restriction (the table has none today).
