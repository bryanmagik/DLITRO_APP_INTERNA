--- ROOT CAUSE OF THE PRIOR seq4 FAILURE (confirmed with evidence) ---
The original file ran 4 sequential preparador UPDATEs against ONE shared pedido row.
Before the vuelto fix, case 1 (estado tomado->en_preparacion) always raised an exception
and its UPDATE was rolled back by the implicit PL/pgSQL savepoint, so the row stayed at
estado='tomado' for every later case. The old case 4 (comanda_impresa only) then correctly
DENY'd, because 'tomado' is not in {en_preparacion,listo}. Its own ALLOW-branch text even
said "unexpected: current estado is tomado" -- direct evidence the author assumed that state.
After the vuelto fix, case 1 legitimately SUCCEEDS and persists estado='en_preparacion' on
that same shared row. Case 4 then runs against estado='en_preparacion' (already an allowed
value), so it correctly ALLOWs -- flipping the old hardcoded DENY expectation. Classification:
TEST ORDER DEPENDENCY, confirmed with code evidence, not a security regression.

--- SECOND ISSUE FOUND AND FIXED DURING THIS PASS (not present before) ---
The first isolated-fixture rewrite of Caso D (preparador on a Branch B pedido) reported a
false ALLOW, because it only checked for a thrown exception. RLS USING-clause denial on
UPDATE does not raise an exception -- it silently matches 0 rows. A standalone diagnostic
(BEGIN...ROLLBACK, not part of the suite) confirmed 0 rows updated AND 0 rows visible via
SELECT for a Branch-A preparador against a Branch-B pedido -- i.e. no real bypass ever
existed. Fixed by adding GET DIAGNOSTICS ROW_COUNT checks to every preparador/pedido case.
Classification: TEST BUG (detection-method flaw in the new test code), not a security bug.
